# 上游更新后怎么同步

结论先说：**有三条路，按省事程度排**。这个 APK 不是官方产物，所有 Android 适配都是三处补丁 + 一条构建链，同步的本质就是"重新走一遍这条链"。

## 先说清楚：我们和上游差在哪

一共只改了 4 个地方，其余完全是上游源码原样：

| 位置 | 改了什么 | 为什么必须保留 |
| --- | --- | --- |
| `end/android_dns.go`（新增） | 没有 `/etc/resolv.conf` 时用系统 DNS 或内置公共 DNS | 否则 Android 上所有域名解析失败 |
| `end/main.go` | 先 `setupDNSServers()`；`import _ "time/tzdata"` | 内嵌时区，否则时间全 UTC |
| `end/cmd/index.go` | 加了 `[stage]` 阶段标记；mDNS 初始化失败不再 `panic` | 手机上组播常被限，不能让 mDNS 带崩服务端 |
| `end/go.mod` + `end/third_party/xsys` | vendored `golang.org/x/sys`，改 `cpu` 包的 HWCAP 探测 | 不改就在 init 阶段崩（就是最早那个崩溃） |

再加上 APK 工程本身（`wpan-apk/`：前台服务、Manifest、图标、keystore）和 `assets/`（`conf/config.yaml`、`sql/init_data.sql`、`certs/cacert.pem`）。

## 路线一：让我来做（最省事，推荐）

把上游信息发我就行，我会重出包：

- 只要说"上游更新了"，我会去查最新 release tag 并重建；或直接给我 tag / commit（比如 `v2027.01.01`）；
- 如果上游改了 `main.go`、`cmd/index.go`、`go.mod`、`sql/init_data.sql`、`conf/config.release.yaml` 这些被我们动过的文件，我会重新对齐补丁——这一步机器容易出错，人判更保险。

## 路线二：自己一条命令构建

`sync-upstream.sh` 已放在 `wpan-apk/` 里，逻辑就是我这次手动做的事：

```sh
# 依赖：git、go 1.25+、JDK17、Android SDK（build-tools;34.0.0 + platforms;android-34）
sh sync-upstream.sh                        # 自动取最新 release tag
REF=v2027.01.01 sh sync-upstream.sh        # 指定 tag
REF=origin/main sh sync-upstream.sh        # 跟 main 分支
SKIP_APK=1 sh sync-upstream.sh             # 只编二进制（想先在 Termux 里试）
APK_VERSION_NAME=1.2.0 sh sync-upstream.sh # 指定 versionName
```

脚本依次做：克隆/更新上游 → checkout 目标 ref → 打 `patches/android-server.patch` → 重新 vendor x/sys 并打 HWCAP 补丁 → 用上游的 `config.release.yaml`、`init_data.sql` 刷新 `assets/` → 交叉编译 arm64 与 amd64 → `build-apk.sh` 出包（versionCode 自动 +1，同一个 keystore 签名）。

Windows 上用 Git Bash 跑（原生 cmd 不行，脚本是 POSIX sh）。

补丁打不上时脚本会停下并提示"上游改了相关段落"——这时候把冲突文件发我，我按新代码重出补丁，别硬顶着 `-f` 强打。

## 路线三：长期维护，做自己的 fork

如果你打算长期跟版，最干净的是 fork 一份：

1. fork `leftScience/wpan` 到你自己的 GitHub；
2. 把上面 4 处改动作为**一个 commit** 推上去（说明写清 "Android 适配"）；
3. 以后更新：`git fetch upstream && git merge upstream/main`，冲突只会出现在那几个文件，解决后 `sh sync-upstream.sh` 出包。

好处是补丁有版本历史，上游哪天把 `end/` 重构了，你能一眼看出自己那 4 处该往哪挪。

## 几个必须注意的点

- **keystore 绝对不能换**（`wpan-apk/keystore/wpan.jks`，alias `wpan`，口令 `wpan123456`）。换了签名就只能卸载重装，本地数据库和已录入的网盘配置全丢。**建议把这个文件连口令一起备份**，它比 APK 重要。
- **配置别手工改 `assets/conf/config.yaml` 的项名**：脚本每次从上游 `config.release.yaml` 重新生成，只做两处手机化调整（`logger.MaxSize: 2`、`update.manifestUrl: ""`）。如果你在手机上改过 `files/wpan/conf/config.yaml`，覆盖安装不会动它；但上游新增的配置项不会自动补进去——上游若加了必填项，把它加进那台机器的 `conf/config.yaml` 即可。
- **数据库自动迁移**：服务端 `DB.AutoMigrate` 默认开，升级后首次启动会自己补表结构，正常情况下覆盖安装即升级，不用导数据。保险起见升级前把 `files/wpan/data/ohome.db` 复制一份。
- **二进制版本号**：脚本会把 `Commit` 取成上游 commit、`RuntimeVersion` 取成上游 `end/runtime-version.txt`（若有）。这是服务端探测版本用的，别丢，否则 App 端可能提示版本不匹配。
- **只想跟随、又不想每次打两个 ABI**：`lib/x86_64` 是给 Intel 设备/模拟器的；真机 arm64 用不到，删掉那段能省 14 MB。

## 上游结构变了怎么办

脚本每一步都假设：`end/` 是服务端（module `ohome`）、`end/conf/config.release.yaml`、`end/sql/init_data.sql`、`end/runtime-version.txt`。如果上游改了这些路径，脚本会在对应步骤直接报"文件不存在"，按报错改脚本顶部几行即可；改动大就回到路线一，把新仓库结构发我。
